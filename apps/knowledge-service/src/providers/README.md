# Provider accounting authority (P6 in progress)

`ProviderLedger` is a service-owned Effect SQL module over a private SQLite accounting file. Staging and production must share this file on the single CX33. Library snapshots, namespace resets, or a Runner restart must not create a new campaign/month allowance. Its authenticated HTTP facade and Runner transport composition are implemented and tested against synthetic HTTP providers. Private R2 retention, concrete X normalization and live validation remain incomplete; this is not a completed acquisition feature.

Every acquisition operation keeps immutable job/window/namespace, input, plan identity, provider/platform/retrieval reserves, start intent, exact run/storage/build identities, raw-page checkpoints, and observed costs. A start permit is issued once. Its lost response leaves an unresolved liability; only exact response evidence or a trusted operator reconciliation can identify or dismiss an ambiguous start. Unknown/running work blocks another provider dispatch across namespaces.

Budgets use integer nanodollars and upward rounding of reported USD. The job limit is USD 0.25, the UTC start-month limit USD 5, and the acceptance campaign USD 2. Prior known usage is imported idempotently with an evidence digest. The Actor event ceiling is distinct from its bounded platform-usage reserve. Stable reported run usage replaces those reserves only after terminal evidence, two matching cost samples separated by at least ten seconds, and archive completion. The retrieval allowance remains conservatively booked; it is not represented as a measured provider charge. Late increased costs remain visible, and an overcharge quarantines new spending.

No configuration means no paid permission. The production entry point requires an absolute `WIKI_PROVIDER_LEDGER_FILE` outside `WIKI_DATA_DIR`, plus `WIKI_NAMESPACE=staging|production`. Both deployed namespaces must use the same file. Without that configuration, the provider facade denies paid permissions even if an unrelated local file was provisioned. Provisioning and absent-run reconciliation are trusted Service/operator methods, not Runner-facing APIs. Hashes refer to evidence; they do not independently prove privacy, pricing or ownership. The provisioned immutable profile supplies event, platform and retrieval reserves; Runner cannot select smaller reservations through HTTP. Input admission excludes arbitrary search, alternate modes and output-dropping options.

`JobProviders` derives the acquisition window from the persisted job start and checks Runner identity, instance, epoch, stage and deadline. Before the independent accounting transaction can issue a permit, a separate committed job transaction records the remote cleanup obligation. A second ownership check serializes permit consumption with cancellation. A crash between databases is conservative; reconciliation never treats local process cleanup as proof that a remote Actor stopped. Status/retention recovery uses a current Runner credential and namespace membership after a lease expires or cancellation commits, while fresh dispatch remains forbidden. Terminal execution can clear the execution obligation; cost and raw retention liabilities remain separate. Pending-operation discovery permits restart without relying solely on the local spool.

The [Runner adapter](../../../runner/src/apify/README.md) now uses these APIs for dispatch, adoption, status and stop. Shared physical pipeline admission, exact-Actor normalization, R2 upload/readback and live privacy/accounting checks remain before P6 closes.

Ordinary checks make no provider calls.
