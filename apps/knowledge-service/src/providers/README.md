# Provider accounting authority (P6 in progress)

`ProviderLedger` is a service-owned Effect SQL module over a private SQLite accounting file. Staging and production must share this file on the single CX33. Library snapshots, namespace resets, or a Runner restart must not create a new campaign/month allowance. Its authenticated HTTP facade, Runner transport, private R2 archive and pinned X output normalization are implemented. End-to-end processor/job composition and live Apify validation remain incomplete; this is not a completed acquisition feature.

Every acquisition operation keeps immutable job/window/namespace, input, plan identity, provider/platform/retrieval reserves, start intent, exact run/storage/build identities, raw-page checkpoints, and observed costs. A start permit is issued once. Its lost response leaves an unresolved liability; only exact response evidence or a trusted operator reconciliation can identify or dismiss an ambiguous start. Unknown/running work blocks another provider dispatch across namespaces.

Budgets use integer nanodollars and upward rounding of reported USD. The job limit is USD 0.25, the UTC start-month limit USD 5, and the acceptance campaign USD 2. Prior known usage is imported idempotently with an evidence digest. The Actor event ceiling is distinct from its bounded platform-usage reserve. Stable reported run usage replaces those reserves only after terminal evidence, two matching cost samples separated by at least ten seconds, and archive completion. The retrieval allowance remains conservatively booked; it is not represented as a measured provider charge. Late increased costs remain visible, and an overcharge quarantines new spending.

No configuration means no paid permission. The production entry point requires an absolute `WIKI_PROVIDER_LEDGER_FILE` outside `WIKI_DATA_DIR`, plus `WIKI_NAMESPACE=staging|production`. Both deployed namespaces must use the same file. Without that configuration, the provider facade denies paid permissions even if an unrelated local file was provisioned. Provisioning and absent-run reconciliation are trusted Service/operator methods, not Runner-facing APIs. Hashes refer to evidence; they do not independently prove privacy, pricing or ownership. The provisioned immutable profile supplies event, platform and retrieval reserves; Runner cannot select smaller reservations through HTTP. Input admission excludes arbitrary search, alternate modes and output-dropping options.

`JobProviders` derives the acquisition window from the persisted job start and checks Runner identity, instance, epoch, stage and deadline. Before the independent accounting transaction can issue a permit, a separate committed job transaction records the remote cleanup obligation. A second ownership check serializes permit consumption with cancellation. A crash between databases is conservative; reconciliation never treats local process cleanup as proof that a remote Actor stopped. Status/retention recovery uses a current Runner credential and namespace membership after a lease expires or cancellation commits, while fresh dispatch remains forbidden. Terminal execution can clear the execution obligation; cost and raw retention liabilities remain separate. Pending-operation discovery permits restart without relying solely on the local spool.

The [Runner adapter](../../../runner/src/apify/README.md) uses these APIs for dispatch, adoption, status, stop and terminal raw retention. Shared physical pipeline admission, prepared-capture composition and live Apify privacy/accounting checks remain before P6 closes.

The production provider configuration also requires `WIKI_R2_CREDENTIALS_FILE`: an absolute path to a private regular JSON file containing `endpoint`, `bucket`, `region`, `accessKeyId` and `secretAccessKey`. Only the Service reads it. `RawArchive` uses Bun's S3 signer, a conditional `If-None-Match: *` PUT, bounded readback and SHA-256 verification. R2 supports atomic conditional writes; a negative read after an uncertain write is not proof of absence. See [R2 conditional operations](https://developers.cloudflare.com/r2/api/s3/extensions/) and [Bun S3](https://bun.com/docs/runtime/s3).

Raw page identity and capacity are durably reserved before upload. Pending writes count toward the 64 MiB job ceiling and cannot be reset by restarting. Verified page manifests become library assets scoped to the originating job; publishing another job cannot reference an unpublished foreign asset. Original bytes stay in R2; the library stores immutable manifests and normalized text. Publication rechecks archive bytes before its commit intent. Archive completion requires matching terminal run metadata and contiguous dataset pages through the observed terminal total. It does not claim that X coverage is exhaustive.

Runner fsyncs raw responses before asking the Service to retain them. A lost upload acknowledgment replays the same bytes, including run metadata whose cost fields may later change. Cost reconciliation remains independent. The stage R2 integration probe verified conditional PUT, identical retry, checksum readback, conflicting-write rejection and unsigned S3 denial. R2 returned HTTP 400 with XML `InvalidArgument` / `Authorization` for unsigned requests; arbitrary 400/404/5xx responses are not accepted as access evidence. This probe is separate from the pending real Apify private-creation check.

Checks: `mise exec -- bun test tests/provider-ledger.test.ts`. Synthetic coverage includes actual concurrent OS processes against one accounting database, SIGKILL after a persisted dispatch intent, namespace-shared quotas, UTC rollover, repeated/late status and cost updates, cancellation, immutable bounded page registration and fresh-connection recovery. Ordinary checks make no provider calls.

Integration checks: `mise exec -- moon run knowledge-service:build` followed by `mise exec -- bun test tests/provider-jobs.test.ts tests/provider-http.test.ts`. These exercise real job and accounting databases, the built HTTP Service, the typed Runner adapter, revocation, cancellation/restart reconciliation and a synthetic provider HTTP server. Full canonical verification also checks the default disabled configuration and generated OpenAPI/JSON Schema contracts.
