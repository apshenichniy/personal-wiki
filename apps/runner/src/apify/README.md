# Apify boundary (P6 in progress)

The transport, local dispatch journal, authenticated Service adapter, raw retention and pinned X normalization are implemented and tested. `processor.ts` and `ingest.ts` compose P5 with the durable Service job APIs; `acquire.ts` claims one job and stops at prepared capture without model execution or publication. Live permission requires the private Service provisioning and privacy gate in the [operations guide](../../../../docs/operations/acquisition.md).

`http.ts` uses a single asynchronous Actor POST with an explicit build number, 256 MiB memory, a positive timeout inside the acquisition window, `restartOnError=false`, and an event charge ceiling. It has no automatic retry, redirect, last-run, reboot or resurrect path. The event charge limit does not replace the platform/retrieval reservation in the Service ledger. A failed or malformed start response is uncertain, not evidence of absence. Tokens are redacted at the configuration boundary and sent only in the Authorization header. Failure objects exclude request URLs, source content, credentials and provider response text.

Status and abort use exact run IDs. An abort response can still be `ABORTING`; only a later terminal observation can release execution ownership. Dataset requests use explicit offsets and bounded limits. Response bytes are counted after fetch decompression and before JSON parsing, capped at 16 MiB and the job's remaining allowance. Missing or inconsistent pagination fails rather than declaring completeness. The caller must retain bytes through the Service and checkpoint each verified page before advancing its offset.

`dispatch.ts` fsyncs a private, exclusive local intent before asking the Service for its one-use permit. It fsyncs the exact start response before acknowledging the run to the Service. Recovery can adopt a complete retained response without another permit or POST. An intent without a complete response stays unresolved after permission was issued. If the Service proves the operation remains reserved, recovery may consume that same unissued permit; the atomic Service check still allows only one POST. A failed permit acknowledgment is also conservative: the caller must consult authoritative Service state or operator evidence rather than removing the marker and retrying. Files must remain in a private, supervisor-owned directory outside the public checkout, inaccessible to Codex. Physical Runner exclusivity remains a separate P7 obligation.

The journal accepts callbacks for permit, receipt acknowledgment and uncertain-state notification. `service.ts` binds those callbacks to the typed authenticated Service API, obtains pinned configuration there, and adopts known operations before considering new dispatch. The Service checks job ownership, deadlines, namespace and operation identity and computes reservations from its provisioned profile. Pending operations, including unresolved starts, are discoverable through that API after restart. `refresh` records authenticated exact-run observations; an unclassified failure does not automatically become retryable. A test-only transport origin accepts loopback HTTP exclusively; the production default is `https://api.apify.com`.

Checks: `mise exec -- bun test tests/apify-http.test.ts tests/apify-dispatch.test.ts`. These tests use an actual loopback HTTP server and synthetic data, including gzip expansion, pagination inconsistencies, lost start/abort responses, acknowledgment recovery and SIGKILL of real child processes after durable intent and receipt checkpoints. They make no paid provider calls.

`retention.ts` fsyncs the exact terminal response/page before a Service upload. The same operation and page offset reuse those bytes after a failed upload; verified pages resume from the Service manifest. Each page is independently bounded, and all operations share the job byte allowance. Neither cancellation nor an expired acquisition window deletes an existing retention obligation. Retention invokes no Actor start.

`xquik.ts` maps raw/nested rows without flattening quote previews or discarding diagnostic-row positions. It preserves original long text, explicit parent metadata and article previews as distinct from actual bodies. Processor Article IDs are mapped through retained containing-post evidence to the Actor's `articleTweetIds` option. The caller must reconstruct this map from retained pages when replaying a plan. External/media references are inert metadata, not additional fetch targets.

Additional checks: `mise exec -- bun test tests/apify-retention.test.ts tests/xquik.test.ts`. `tests/acquisition-pipeline.test.ts` covers acquisition-to-prepared composition and Service restart without another POST. Live prepared-capture validation remains outstanding.

`recovery.ts` distinguishes remote execution from terminal retention/accounting debt. Unknown or running operations block acquisition; terminal debt preserves liability and is retried separately with a private fsynced backoff journal. Capacity failure is actionable and never causes repeated oversized downloads. Accounting refresh continues even if archival fails.

Provider contracts: [start](https://docs.apify.com/api/v2/actors-runs-post), [dataset pagination](https://docs.apify.com/api/v2/dataset-items-get), [abort](https://docs.apify.com/api/v2/actor-run-abort-post).
